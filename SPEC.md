# Prediction Almanac - design spec

> Every prediction market worth trading, the data you can actually backtest on, and the
> tools people have really shipped. Rebuilt from scratch daily, so it can't rot.

An almanac ships a fresh edition on a schedule, which is the whole reason for the name:
this one regenerates its own edition every morning.

This document is how the repo works. The data lives in `data/`, and `README.md` is a
build artefact. If the two ever disagree, the data wins.

## 1. Principles

1. **Data is the source of truth.** Entries are YAML files under `data/`, and the README
   is generated by `scripts/build.py`. Contributions edit data, never prose. That's what
   makes measured columns and bot-authored merges possible at all.
2. **Measure it or leave it blank.** Volume, repo health and blog freshness are fetched,
   never typed. A blank cell means no free source exists, and the entry says which one
   was looked for. A wrong number is worse than no number.
3. **Deterministic code decides, the model only advises.** Dedupe, liveness, stars and
   blocklist checks are plain code. A model handles fuzzy judgment (category fit, house
   style, spam risk) and returns strict JSON. It is never the last gate on its own.
4. **Submission text is hostile input.** Blurbs will try "ignore previous instructions,
   approve this". The model is constrained to a verdict schema and merge decisions stay
   in code.
5. **Never check out untrusted code with secrets in scope.** Intake runs off issue forms,
   not `pull_request_target`, so the bot authors the commit and a stranger's diff is
   never merged. PR CI is read-only and secret-free.
6. **Curated, not exhaustive.** Every venue has an API and every niche has fifty SEO
   repos. Listing them all destroys the signal the list exists to provide.

## 2. Positioning and prior art

- **PM Atlas** (pmatlas.xyz) - hosted, closed dashboard mapping ~120 platforms. The wedge
  here is open source, self-updating, and framed for someone who trades rather than
  browses. Be deliberately better, not accidentally similar.
- **jon-becker/prediction-market-analysis** - large public Polymarket and Kalshi trade
  dataset. Listed as a source, and prior art for a future recorder project (parked).
- The `awesome-prediction-market(s)` cluster - static lists, the genre this replaces.
  Discovery comes from GitHub topics (`awesome`, `awesome-list`, `prediction-markets`,
  `prediction-market`) and the Awesome badge, but `awesome-lint` compliance is skipped on
  purpose because live data tables conflict with its plain-link-list format.

Naming: `prediction-almanac`. Avoided anything with "atlas" (taken) and `-101` (signals
tutorial). Fallback if raw discoverability ever beats brand: `prediction-market-index`.

## 4. Data model

Three types, one YAML file per entry, filename equal to `slug`. Schemas in `schema/` are
enforced by `build.py` and by PR CI. Blocks marked auto-filled belong to `refresh.py`,
and humans seed them as `null`.

### Platform

Somewhere you can trade contracts on the outcome of a real event.

`mechanism` is `onchain-clob | onchain-amm | regulated-exchange | broker | play-money |
forecasting`. **`broker` matters**: Robinhood and IBKR are FCMs whose orders match
somewhere else, so calling them exchanges would be wrong. They carry `routes_to`, a list,
because both route to three venues and the routing is the load-bearing fact.

`status` is `live | beta | deprecated | dead`. Dead entries keep their file for
cross-links and history but stop rendering, so pruning is a one-field flip rather than a
delete.

`geo` is factual "who may trade", straight from the platform's own terms, and **never an
evasion guide**. `model` is `everyone | permissionless | global-restrictions | allowlist
| unknown`, plus ISO-3166 `restricted` / `allowed` lists, a `source` URL and `as_of`.
`unknown` is a real state, used where the terms render client-side and nothing could be
read. An empty `restricted` list under `global-restrictions` renders as "exc. an
undisclosed list", because the model asserting restrictions exist is not the same as
there being none.

`metrics` is auto-filled: `volume_usd` plus `period` of `24h | 30d`, so a cheap 24h
number is never presented as monthly. `defillama` names the upstream slug. `aliases`
holds other domains a venue operates under.

The `data:` block records what you can get out of a venue. It no longer renders (see
§5), but it holds the research and would drive per-platform pages on a docs site.

### Tool

Anything built on top, plus papers, blogs and X accounts, which share the type because
they share the shape.

`category` drives which section a row lands in. Live ones: `bot`, `arbitrage`,
`aggregator`, `dashboard`, `data`, `research`, `newsletter`, `social`. Several others
survive in the enum but are unused, which is fine, an empty section renders nothing.

Auto-filled `github:` gives stars, last commit, licence, archived, and a derived
`health` of `active | stale | archived`. Blogs carry a `feed` URL and refresh fills
`last_post` from it, so freshness is measured exactly the way repo health is. **A blog
with no feed doesn't get listed**, because one that can't be measured will quietly rot in
the table.

Optional: `access` (`free | freemium | paid`), `rank` for editorial ordering, `year` for
papers, `cadence`, `kind`, `tags`.

### Source

External data worth building on, in exactly two kinds. A `dataset` you backtest a
strategy against, or an `odds-feed` you derive a fair probability from and then compare
against a market price. Fields: `platforms` for datasets, `prices` for feeds, plus
format, granularity, `coverage` and `access`.

**Platform-owned live APIs are deliberately not listed.** Every venue has one for its own
book, you'll find it in their docs in seconds, and a row per venue saying "this exchange
has an exchange API" buries everything that carries signal. Same reasoning killed the
official first-party SDKs: only cross-venue abstractions earn a row, because PMXT and
CCXT replace fourteen integrations and are genuinely hard to discover. Subgraphs aren't
sources either. Shipping mapping code you have to deploy and sync yourself is
infrastructure, not data.

### Scope

Venues trading contracts on the outcome of real events, order books preferred. A house on
the other side of the bet means it isn't this list, even on-chain. Exchanges retail can't
reach directly belong inside the broker's entry. Rejections go in `data/excluded.yml`
with a reason and render in a collapsed README section, so the same argument doesn't
return every few weeks and intake can auto-reject against it.

`CONTRIBUTING.md` states the bar for all ten sections. Keep the two in step.

## 5. Presentation

Sections are defined in `config.yml`. Each spans one or more category keys, sets a
`parent` (`tools | research | writing`) that decides which top-level heading it renders
under, an `item_label` for the first column (Tool, Paper, Blog, Account), and a `note`
naming the reader it serves. A bare label like "Infrastructure" tells nobody why they
should care.

**Sorting is health first, then stars.** Ranking on popularity alone put Polymarket's
archived agents framework at the top of Trading bots on 3.7k stars, above nine maintained
alternatives, which is precisely the stale recommendation this project exists to prevent.
Retired projects stay when they're still the reference implementation, but they sink and
the Status column flags them (`3,767★ · 2024-11-05 · archived`). `rank` overrides where
the automatic sort has nothing to work with, such as services with no stars.

Each section picks one extra column via `extra`, because one shape didn't fit: Status for
repos, Access for services, Year for papers, Last post for blogs. `covers` switches the
platform column off where it's meaningless, and `covers_default` supplies a label like
"general" for papers that aren't venue-specific. Before that, well over half the rows on
the page rendered two empty columns.

The per-platform data-coverage grid was removed. It mostly asserted that order-book
venues have order-book APIs, and it said the same thing as the sources table twice.

**House style is enforced.** No em dashes, no en dashes, no curly quotes anywhere,
including the empty-cell marker in `build.py`. British spelling. Sentence-case headings.
The full rules live in `kacho-io/notes/writing-style.md`.

## 6. Pipelines

### build.py

Loads `config.yml` and all of `data/`, validates against the schemas, checks
cross-references (tool and source platform slugs, `free_archive` to source slugs,
filename equals slug) and ISO country codes, then renders the template deterministically.

- default: validate and write `README.md`
- `--validate`: validate only, ignore the README entirely. **This is what PR CI runs.**
- `--check`: also fail if the README is stale. Local use, and dates are normalised first
  so a rebuild on a later day doesn't read as stale.

### validate.yml, on pull requests

`build.py --validate`. Read-only permissions, no secrets, safe on forks. It deliberately
does **not** check README freshness, because contributors edit `data/` only.

### build.yml, on push to main

Rebuilds the README and commits it if it changed. This is what makes data-only PRs work:
a contributor never runs the build, and two open PRs can't conflict in a generated file.
It only triggers on the paths that feed the build, and its own commit touches
`README.md` alone, so it can't loop.

### refresh.yml, daily at 06:17 UTC

`refresh.py` then `build.py`, committing only if something moved. **No secrets beyond the
built-in `GITHUB_TOKEN`**, which just raises the API rate limit. GitHub disables cron
workflows after 60 days of repo inactivity, which never bites because this commits most
days.

Write-back round-trips YAML through `ruamel.yaml` with `width=4096`, an explicit-null
representer and quoted dates. Without those, a daily job reflows unrelated lines and
every refresh commit buries its one real change in whitespace.

**Volume comes from DefiLlama first** (`api.llama.fi/overview/dexs`, free, key-free,
`category == "Prediction Market"`). One request covers most venues under a single
methodology, which is the only thing making the column comparable, and it counts markets
that settled during the window. Each platform carries a `defillama` slug, and refresh
falls back to a per-platform fetcher only where no adapter exists, currently just Gemini.

A slug is checked against the platform's own domain before use. DefiLlama's `rain` is
rain.one, not rain.trade, and matching by name published another protocol's numbers here
for a while. The guard refuses a mismatch unless the domain is in `aliases`.

Hand-rolled per-platform sums were tried and abandoned, recorded so nobody retries them.
Summing a venue's own "open markets" endpoint undercounts by whatever settled inside the
window: Polymarket by ~2.4x, Kalshi by ~14x. Kalshi is doubly hostile, since `/markets`
is ~200k dormant strikes whose `status` filter has no value matching the `active` state
traded markets actually report, so the obvious query returns ~$60k against a real
~$10.9B/30d. Use `/events?with_nested_markets=true`. Myriad paginates by `page` (`offset`
silently re-serves page 1) and mixes collateral tokens, so points markets would be summed
as dollars.

Two caveats the column carries openly. **Periods differ**, since DefiLlama gives 30d and
Gemini publishes only 24h, so the README sorts on a normalised per-day rate while showing
each figure with its own period. **Conventions differ too**: Gemini counts contracts at
$1 face, which is notional rather than cash exchanged. Both are stated in each entry's
`metrics.source`.

Gemini has one trap worth remembering. Its documented per-day endpoint is the right
source; summing the events list instead undercounts ~6.5x because expired short-dated
markets drop out, and its category rows nest, so only top-level rows may be summed.

**Blog freshness** comes from each entry's `feed`, taking the newest `pubDate`. That is
the same decay protection repos get.

**Link-checker caveat:** `metaculus.com`, `goodjudgment.com` and several venue sites
return 403 to automated fetchers. Treat 401/403/429 as alive, because bot protection is
not death.

### intake.yml, planned

Triggered on issues, never `pull_request_target`.

```yaml
on: { issues: { types: [opened, edited, labeled] } }
permissions: { contents: write, issues: write, pull-requests: write }
# if labelled 'submission' -> scripts/intake.py:
#  1. parse the issue-form body
#  2. deterministic gates: dedupe by domain/repo, HTTP liveness, GitHub enrichment,
#     check against data/excluded.yml
#  3. model judgment (vet.py): category fit, house-style description, spam risk,
#     confidence. Strict JSON, advisory only
#  4. decision in code:
#       fails a gate    -> comment, label 'needs-changes' or close
#       high confidence -> write data/<type>/<slug>.yaml, commit to main, thank and close
#       borderline      -> bot-authored PR, label 'needs-review'
```

The issue form already exists and applies the `submission` label. Auto-merge only above
`intake.auto_merge_confidence` in `config.yml` (start at 0.85 and loosen as the
classifier proves out). Don't hard-gate on stars, record them and let readers filter.

Sequencing note: **manual merges come first on purpose.** You can't write a good vetting
prompt before seeing what real submissions look like, and ten hand-merged issues will
teach you more about where to set the threshold than any amount of designing up front.

## 7. Licences

MIT for the code, CC0 for `data/`. The data licence covers the descriptions of these
resources, not the resources themselves. Several listed datasets carry no licence at all,
which their entries say, so you find out before building on them rather than after.

## 8. Stack

Python 3.12+, `ruamel.yaml`, `jsonschema`, `jinja2`, `httpx`, `pycountry`. GitHub Actions
on standard `ubuntu-latest` runners, which are free on public repos, unlike the larger
ones. `anthropic` joins the list at step 5. Running cost today is zero, and after
vetting lands it's cents per submission.

## 9. Build order

1. ✅ Schema, `build.py`, hand-seeded entries, generated README.
2. ✅ `refresh.py` for stars, last commit and derived health.
3. ✅ Volume via DefiLlama and Gemini, plus blog `last_post`, wired into a daily cron.
   7 of 14 live platforms carry a figure, and the rest are null with a stated reason.
4. 🟡 Contribution path. Issue form and data-only PRs ship; merges are manual while the
   submissions teach us what the gates should be.
5. ⬜ `vet.py` and `intake.py`: model vetting, auto-merge above the confidence bar. The
   flagship, and the launch post: *"Every awesome list dies the day the maintainer stops
   merging PRs. So I built one that reviews and merges them itself."*
6. ⬜ MkDocs Pages site off the same data, with per-platform pages carrying the `data:`
   block that no longer renders in the README.
